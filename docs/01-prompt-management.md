# 1. 프롬프트 관리 (Prompt Management)

## 1.0 목적과 범위

PentAGI 에이전트 실행에 사용되는 프롬프트(태스크 지시문, 정찰/스캐닝/익스플로잇 검증 템플릿, 리포트·알림 문구 등)를 체계적으로 생성·검토·재사용하기 위한 계획이다.

- 대상: 사내에서 사전 승인된 자산에 대한 침투테스트 업무에 한정한다. 비인가 대상에 대한 스캔·공격 프롬프트는 작성·승인 대상에서 제외한다.
- 본 레포에는 실제 고객·거래 데이터, 운영 도메인/IP, 자격증명 등 식별정보를 포함하지 않는다. 프롬프트는 변수(placeholder)로 파라미터화하고, 실 데이터는 별도 접근제어된 저장소에서 관리한다(저장소 지정은 확인 필요).

## 1.1 프롬프트 생성

### 1.1.1 분류 체계

| 축 | 값 | 비고 |
|---|---|---|
| 유형 | 정찰(Recon) / 취약점 탐지 / 익스플로잇 검증 / 리포트 생성 / 알림·공지 | PentAGI 에이전트 플로우 기준 |
| 위험도 | Low / Medium / High | 실행 시 대상 시스템에 미치는 영향(서비스 중단 가능성 등) 기준 |
| 대상 태그 | 예: payment-api, admin-console 등 | 실제 식별정보 대신 내부 코드명 사용 |

### 1.1.2 작성 절차

1. 표준 템플릿([prompts/_template.md](../prompts/_template.md))으로 초안 작성 — 목적, 범위, 전제조건(사전 승인 범위), 기대 출력, 위험도, 실패 시 롤백/중단 방법 포함
2. 보안 검토 — 파괴적 동작(실 서비스 중단·데이터 삭제 유발 가능성) 포함 여부 확인
3. 컴플라이언스 확인 — 개인정보·거래데이터 노출 가능성 점검(개인정보보호법·전자금융감독규정 적용 여부는 법무 검토 필요)
4. 지정 승인자 승인
5. 버전 태깅 후 카탈로그 등록

### 1.1.3 필수 메타데이터 (프롬프트 파일 프론트매터)

| 필드 | 설명 |
|---|---|
| id | 고유 식별자 |
| version | 날짜 기반 또는 semver |
| author / approver | 작성자·승인자 |
| risk_level | Low / Medium / High |
| last_reviewed | 최종 검토일 |
| status | draft / in_review / approved / deprecated |

### 1.1.4 저장 방식

- 본 Git 저장소에 Markdown + YAML 프론트매터로 관리하여 변경 이력을 자동 추적한다.
- 실행 로그·스캔 결과물(고객/거래 데이터 포함 가능)은 본 레포에 저장하지 않는다.

## 1.2 프롬프트 재사용

### 1.2.1 카탈로그 구조 (제안)

```
prompts/
  recon/
    {id}-{slug}.md
  vuln-scan/
  exploit-verify/
  report/
  notice/
```

각 디렉터리 상위에 태그(대상유형·위험도·사용빈도) 기반 인덱스 파일을 유지해 검색성을 높인다.

### 1.2.2 재사용 전 체크리스트

- [ ] 대상 범위가 이번 인가 범위와 일치하는가
- [ ] 최종 검토일 기준 유효기간(제안: 6개월) 이내인가 — 유효기간은 확인 필요
- [ ] 대상 URL·자격증명 등이 하드코딩 없이 변수화되어 있는가
- [ ] High 위험도 프롬프트는 매회 재승인을 받았는가

### 1.2.3 피드백 루프

- 사용 후 결과(성공/실패, 개선사항)를 메타데이터에 기록
- 분기별로 미사용·저효율 프롬프트를 검토해 status를 deprecated로 전환

### 1.2.4 접근 제어 및 감사

- 프롬프트 조회·실행 권한은 인가된 보안 담당자로 제한
- 누가 언제 어떤 프롬프트를 재사용했는지 감사 로그로 기록

## 1.3 향후 확장 항목 (상위 관리계획 다른 섹션에서 다룰 예정)

- 실행 이력/리포트 관리
- 대상 자산(인벤토리) 관리
- 승인 워크플로우 자동화

---

**리스크 / 반대 시각**

- 카탈로그·메타데이터 체계가 과도하게 무거우면(승인 단계, 필수 필드 다수) 실제 팀 규모 대비 운영 부담이 커져 형식만 남고 지켜지지 않을 위험이 있다. 팀 인원과 점검 빈도에 맞춰 필드·승인 단계 수를 조정하는 것을 권장한다.
- "6개월 유효기간", "저장소 분리" 등은 현재 확인되지 않은 제안값이므로, 실제 운영 정책(보안팀/법무 협의)으로 확정 전까지는 초안으로 취급해야 한다.
